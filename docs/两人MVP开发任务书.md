# 跨境工业品 AI 售前平台｜两人 MVP 开发任务书

**版本**：0.1  
**适用范围**：国内工业品卖家、海外买方的小范围 MVP 试点  
**目标**：两个人按本任务书完成一条可在正式产品界面中操作的闭环：

`产品资料核准 → 产品页发布 → 买方描述需求 → 需求确认 → 规则推荐 → 有据问答/人工接管 → RFQ → 销售跟进`

本任务书是执行计划，不把 V1、长期功能或聊天开发助手当成产品运行依赖。

## 1. 本轮完成与暂不完成

### 必须完成

- 企业成员可登录并只访问所属企业的数据。
- 管理员可录入至少两个适用条件不同的示例水泵型号。
- 每个型号有来源资料、字段核准记录、产品版本和发布状态。
- 买方可以描述用途、流量、扬程等需求，系统保存原话和需求修订。
- 系统能区分买方已确认、AI 提取候选和缺失条件。
- 推荐结果能显示满足项、冲突项、未知项和产品详情页链接。
- 资料内问题显示答案和来源；资料外问题转人工任务。
- 买方可以提交 RFQ，销售可以查看完整上下文并记录下一步。
- 刷新或重新登录后，产品、会话、推荐、任务、RFQ 和销售状态仍然存在。

### 本轮明确不做

WhatsApp/微信等正式渠道、自动营销序列、CRM 双向同步、实时库存/价格、自动报价/下单、从不完整资料生成工程 CAD、复杂向量知识图谱、多地域高可用和微服务拆分。

## 2. 两个角色

### 角色 A：产品、数据、AI 与验收负责人

负责“系统应该知道什么、什么条件才能推荐、什么话必须转人工，以及结果是否符合业务事实”。

主要产出：字段字典、示例产品资料、核准规则、匹配规则、提示词和测试集、验收记录、业务缺陷优先级。

### 角色 B：应用工程、数据持久化与部署负责人

负责“用户能否在产品界面完成操作，以及数据是否可靠保存、隔离和恢复”。

主要产出：应用骨架、数据库迁移、后台和买方页面、API、文件处理、模型适配层、人工任务、RFQ、权限、日志和部署说明。

两人共同负责：接口字段确认、端到端联调、阻断问题处理和最终验收。任何技术事实、匹配阈值或对外承诺都不能由单人默默决定。

## 3. 开发规则

1. 使用模块化单体；先划清产品、会话、匹配、问答、RFQ 的代码责任，不提前拆微服务。
2. 产品事实只有一个来源。产品页、推荐和 chatbot 都读取已核准产品版本。
3. AI 提取结果默认是候选值，买方确认后才能用于匹配或 RFQ。
4. 推荐和 RFQ 必须保存当时的需求修订、产品版本和规则版本。
5. 所有外部输入和 RFQ 提交使用去重键；重试不能生成第二条业务记录。
6. 每个任务完成后必须有可运行证据，不能用“代码已写”代替验收。
7. 每个阶段都先走成功路径，再走一个失败路径；阻断问题优先，非阻断问题登记后继续。

## 4. 阶段总览与关卡

| 阶段 | 目标 | 主负责人 | 进入条件 | 退出关卡 |
| --- | --- | --- | --- | --- |
| P0 | 统一范围、数据和开发环境 | A+B | 两人确认任务书 | 应用可启动，字段和验收样例已冻结 |
| P1 | M1 产品资料导入与核准 | A 定规则，B 实现 | P0 完成 | 两款产品均可核准，来源可追溯 |
| P2 | M2 产品详情页 | B 实现，A 审核 | P1 有已发布版本 | 发布页与核准版本一致，未发布页不可公开 |
| P3 | M3/M4 需求识别与匹配 | A 定规则，B 实现 | P1/P2 完成 | 买方需求可确认，推荐可复现或明确拒绝推荐 |
| P4 | M5 有据问答与人工接管 | A 定证据边界，B 实现 | 有产品资料和会话 | 资料内回答有引用，资料外生成任务 |
| P5 | M6/M7 RFQ 与销售工作台 | A 定业务字段，B 实现 | P3/P4 完成 | RFQ、负责人、状态和下一步可保存并回看 |
| P6 | 联调、权限和恢复演练 | A+B | P5 完成 | 完整主路径及关键异常路径通过 |

## 5. 具体任务清单

### P0：项目准备

#### A-001 冻结 MVP 业务边界

- 明确本轮只做水泵和网页入口。
- 从本任务书复制一条主验收路径和至少三条失败路径。
- 明确不承诺正式工程选型、价格、库存、交期和成交效果。

**交付物**：`docs/mvp-acceptance.md` 或等价验收清单。  
**完成标准**：B 能据此判断一个功能是否属于本轮；两人对“不做什么”没有分歧。

#### A-002 准备两款示例水泵资料

- 为每款产品准备型号、用途、流量范围、扬程范围、介质适用条件、材质或其他可公开字段。
- 记录每个字段的来源文件和页码/位置。
- 标出至少一个两款产品不同的适用条件，用于后续匹配测试。
- 资料没有授权时只使用明确标注的模拟资料，不暗示真实厂商合作。

**交付物**：样例资料目录、字段表、来源位置表。  
**完成标准**：A 能人工回答每个公开字段来自哪里；B 不需要凭空补参数。

#### A-003 定义最小字段字典与状态

至少定义：产品、来源文件、产品字段、产品版本、会话、消息、需求修订、推荐、答案引用、人工任务、RFQ、线索、跟进记录。

每个关键字段说明类型、单位、是否必填、来源类型和状态，例如“AI 提取候选 / 买方确认 / 未知 / 工程师判断”。

**交付物**：字段字典和状态表。  
**完成标准**：B 可以据此设计数据库和 API，不需要把所有数据塞进不可查询的自由文本。

#### B-001 确认技术栈并建立可重复启动方式

- 确认前端、后端、数据库、文件存储和测试命令。
- 默认采用模块化单体；本地开发可使用 SQLite 或同等轻量数据库，但业务代码不能依赖进程内唯一状态。
- 环境变量只放在本地配置，不提交密钥。

**交付物**：根目录 README 的启动说明、锁定依赖、`.env.example`。  
**完成标准**：新环境按说明能启动应用并运行基础测试。

#### B-002 建立最小数据迁移和租户边界

- 创建企业、成员、角色和审计记录的最小结构。
- 所有私有业务对象带企业归属；查询从登录上下文取得企业，不信任前端单独传入的企业 ID。
- 为后续对象预留稳定 ID、创建时间和更新时间。

**交付物**：初始迁移、种子数据、权限检查。  
**完成标准**：两个企业的测试数据互相不可读取。

#### B-003 建立共享接口约定

至少先约定以下 ID 和关系：`tenantId`、`productId`、`productVersionId`、`conversationId`、`requirementRevisionId`、`recommendationId`、`rfqId`、`taskId`。

**交付物**：接口文档或类型定义。  
**完成标准**：A 的字段字典与 B 的请求/响应字段一致，双方不再用页面文案拼接业务关系。

### P1：M1 产品资料导入与核准

#### A-101 确认产品核准规则

- 定义哪些字段允许 AI/人工录入，哪些字段必须有来源。
- 定义草稿、待核准、已发布、已撤回状态。
- 定义修改已发布关键字段后必须产生新版本的规则。

**完成标准**：任何未经核准字段都不能进入推荐、公开页或确定性问答。

#### A-102 审核两款产品数据

- 逐字段检查数值、单位、适用条件和来源位置。
- 明确缺失和冲突字段，不用默认值掩盖。
- 形成核准记录，包含操作者和时间。

**完成标准**：两款产品各有一份可发布的核准版本和一份可追溯来源清单。

#### B-101 实现产品与来源文件管理

- 产品列表、产品新建、编辑、启用/撤回。
- 文件上传或文件元数据登记，保存哈希、类型、归属、版本和可见范围。
- 文件处理状态显示待处理、成功或失败；失败原因可见。

**完成标准**：新文件不会覆盖旧文件；页面可以看到文件归属和处理状态。

#### B-102 实现字段核对和版本发布

- 显示字段值、单位、来源文件、来源位置、当前状态和修改记录。
- 支持人工修正、核准、撤回和生成产品版本。
- 发布动作记录操作者和时间。

**完成标准**：可以从一个公开参数回到来源文件；修改已发布字段后旧版本仍可读取。

### P2：M2 产品详情页

#### A-201 定义页面展示内容和中英文文案

- 确认首屏、关键参数、适用条件、资料下载、来源/版本提示和询价入口。
- 中英文只翻译展示文案，不改变原始参数、单位和引用。
- 明确“初步展示，正式选型需确认”的边界文案。

**完成标准**：A 能逐项指出页面文字对应的已核准字段或静态说明来源。

#### B-201 实现产品页预览、发布和撤回

- 后台预览必须读取待发布版本。
- 只有已发布版本可以通过公开链接访问。
- 产品页显示版本、来源入口、详情、继续提问和 RFQ 入口。
- 缺失媒体不显示虚假占位能力。

**完成标准**：两个产品都有固定链接；产品资料更新后必须重新发布，旧推荐仍能指向当时版本。

### P3：M3/M4 用户画像与产品匹配

#### A-301 定义需求字段和追问顺序

至少覆盖：品类、用途、流量、扬程、介质、温度/材料（如试点需要）、数量、地区和交期。

- 标出影响推荐的必问字段。
- 区分买方原话、AI 候选、买方确认、销售修正和未知。
- 定义买方拒答后的处理：继续保存、转人工或暂不推荐。

**交付物**：需求字段 schema、追问表、10 条以上中英文测试输入。  
**完成标准**：每个用于匹配的值都能追溯到买方输入或确认动作。

#### A-302 定义可解释匹配规则

- 规则只读取已核准产品字段和已确认需求。
- 输出“可初步推荐 / 条件不足 / 无可靠候选”三类结果。
- 每个候选输出满足项、冲突项、未知项、规则版本和详情页链接。
- 关键阈值标注“示例规则”或由工程负责人确认，不能伪装成正式选型标准。

**交付物**：规则表和至少 6 个匹配测试案例。  
**完成标准**：相同输入、产品版本和规则版本重复运行得到相同结论。

#### B-301 实现买方会话与需求摘要

- 保存原始消息、来源、时间和会话 ID。
- 展示需求摘要卡，区分已确认、待确认和未知。
- 买方可以修正关键字段；修正后产生新的需求修订。
- 页面刷新后会话和摘要可恢复。

**完成标准**：AI 提取不会自动变成买方确认值；历史原话不被覆盖。

#### B-302 实现匹配服务和推荐卡

- 由规则服务计算结果，不让生成式模型直接决定硬条件。
- 保存推荐快照、产品版本、需求修订和规则版本。
- 推荐卡展示理由、限制、详情页链接和继续询价入口。
- 无可靠候选时显示原因并提供转人工/保存线索入口。

**完成标准**：需求修订后旧推荐标为失效并生成新结果。

### P4：M5 有据问答与人工接管

#### A-401 建立问答测试集和引用要求

- 准备至少 5 个资料内问题、5 个资料外或需工程判断的问题。
- 每个资料内问题写出期望答案、原文位置和可接受表达。
- 定义不得猜测的内容：价格、库存、交期、认证、未公开材料和个案适配。

**完成标准**：验收时能判断答案是有依据、无依据还是需要人工判断。

#### A-402 定义人工任务内容和处理规则

人工任务至少包含：原问题、买方确认工况、推荐型号、产品版本、已有回答、缺失原因、负责人和状态。

**完成标准**：工程师无需重新翻找整段聊天即可理解问题；单次人工答复不会自动写入通用产品知识。

#### B-401 实现模型调用边界和有据回答

- 统一记录任务类型、模型、版本、请求状态、耗时和错误。
- 设置超时、限流和失败状态。
- 只向回答模块提供已核准资料或明确的检索结果。
- 输出答案、引用和“无法确认”原因。

**完成标准**：模型超时或无证据时原问题仍被保存，不把技术故障说成产品不适用。

#### B-402 实现人工任务队列

- 买方页面显示转人工状态和下一步说明。
- 后台可按待处理、处理中、已答复查看任务。
- 工程师可提交针对当前会话的回复并记录操作者、时间和引用。

**完成标准**：资料外问题能自动生成任务，销售/工程师能在后台完成处理闭环。

### P5：M6/M7 RFQ 与销售工作台

#### A-501 确认 RFQ 字段和线索阶段

候选字段：产品/型号、已确认工况、数量、目的地、期望交期、联系人、公司、联系方式、自由说明、缺失项和同意状态。

- 明确哪些字段必须由试点销售确认。
- 定义待跟进、技术确认中、待买方补充、可报价、暂缓等阶段。
- 明确“可报价”不是系统自动承诺。

**完成标准**：销售能区分信息不完整和真正可进入报价流程的线索。

#### B-501 实现 RFQ 表单和快照

- 从已确认需求和推荐预填字段，并标出来源。
- 买方可修改；修改关键工况后重新评估推荐。
- 提交前显示摘要，提交后生成唯一 RFQ ID。
- 使用幂等键防止重复点击产生重复 RFQ。

**完成标准**：刷新和重复提交都不会丢失或重复创建记录；RFQ 保留提交时的产品和需求快照。

#### B-502 实现销售工作台

- 线索列表按待处理和跟进日期排序。
- 详情页展示需求、推荐、产品版本、问答、人工任务、RFQ 和时间线。
- 支持负责人、阶段、跟进日期、备注和下一步。
- 逾期任务和未处理技术问题有明显状态。

**完成标准**：销售不需要访问数据库或开发工具即可完成分配、跟进和状态更新。

#### A-502 完成业务验收

- 用真实界面逐条检查字段预填、缺失项、状态变化和中英文切换。
- 检查销售看到的内容是否与买方提交的内容一致。
- 对错误参数、重复 RFQ、资料外问题和拒答场景给出结论。

**交付物**：端到端验收记录和剩余问题清单。

### P6：联调、权限和恢复演练

#### A-601 主路径与异常路径验收

必须执行：

1. 两款产品均成功发布并可访问。
2. 买方给出完整需求并获得推荐。
3. 买方缺少关键条件，系统追问或标记未知。
4. 资料内问题得到带引用的答案。
5. 资料外问题生成人工任务。
6. RFQ 提交后销售能看到完整上下文。
7. 产品更新后旧 RFQ 仍引用旧版本。
8. 两个企业之间不能读取对方资料、会话和 RFQ。

#### B-601 完成安全、备份和运行检查

- 检查所有后台查询、文件访问和任务处理都带企业边界。
- 验证应用重启不会丢会话、RFQ 和任务。
- 完成数据库和关键文件的备份/恢复演练，记录实际耗时和可恢复记录。
- 记录接口错误、模型错误、文件处理失败和待处理任务数量。

**完成标准**：恢复证据和已知限制写入开发状态记录，不能只写“备份已开启”。

## 6. 建议执行节奏

按每周能稳定投入 4–5 个开发日估算，不把日期当成上线承诺。

| 周期 | 角色 A | 角色 B | 联调结果 |
| --- | --- | --- | --- |
| 第 1 周 | 样例资料、字段字典、验收案例 | 项目骨架、迁移、登录/租户 | 应用能启动，两人使用同一数据契约 |
| 第 2 周 | 核准规则和产品页内容 | 产品导入、核准、版本、页面 | 两款产品可核准并预览 |
| 第 3 周 | 需求 schema、追问和匹配规则 | 买方会话、需求摘要、推荐卡 | 从聊天得到可解释推荐 |
| 第 4 周 | 问答测试集和人工规则 | 模型边界、引用、任务队列 | 有据回答和人工接管可用 |
| 第 5 周 | RFQ/线索阶段和业务验收 | RFQ、销售工作台、时间线 | 从买方提交到销售跟进闭环 |
| 第 6 周 | 主路径、异常路径和数据核对 | 权限、错误、备份恢复、部署 | MVP 验收证据齐全 |

如果某阶段出现阻断问题，只修复影响当前主路径的部分；非阻断问题进入清单，不得为了“全部完美”阻塞下一阶段。

## 7. 每周协作机制

### 每日 15 分钟同步

每个人只回答三件事：昨天完成什么、今天完成什么、是否被对方阻塞。阻塞必须具体到接口、字段或验收案例。

### 每个阶段结束时

- A 提供业务验收清单和测试输入。
- B 提供可运行页面、迁移、接口和运行说明。
- 两人共同走一遍主路径和一个失败路径。
- 记录未完成项、影响、临时替代办法和下一阶段复审条件。

### 接口变更规则

任何字段、状态或 ID 变更必须同时更新字段字典、接口类型和测试数据；不允许只改前端或只改数据库后继续联调。

## 8. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才算完成：

- 代码或文档已放入仓库正确位置；
- 有对应的页面操作、接口测试或数据检查证据；
- 失败状态和权限边界已处理；
- 刷新/重启后数据仍可读取（适用时）；
- A 与 B 都知道如何复现和验证；
- 受影响的开发状态记录已更新；
- 未完成内容没有被标记成“已验证”或“已上线”。

## 9. 第一轮直接分配

现在可以直接把以下任务发给两个人：

- **角色 A**：A-001、A-002、A-003；目标是交付两款水泵资料、字段字典和第一版验收清单。
- **角色 B**：B-001、B-002、B-003；目标是交付可启动项目、初始迁移、登录/租户边界和共享接口约定。
- **共同关卡**：只有 P0 通过后，才开始 P1 的产品资料开发。

第一轮不要同时开发 chatbot、复杂 UI 和完整销售系统。先把产品事实、来源、版本和企业边界定稳，后续功能才不会反复返工。
