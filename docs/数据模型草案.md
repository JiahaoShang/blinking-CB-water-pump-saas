# MVP 数据模型草案｜先定关系，随功能建表

**状态**：讨论草案，尚非最终数据库表设计。与 [MVP 开发需求文档](MVP-开发需求文档.md)、[技术架构草案](技术架构草案.md)配套使用。

## 1. 现在决定到什么程度

现在应确定业务对象、归属、关联与不能被覆盖的历史；开发每个 MVP 功能时再落实字段、约束、索引和迁移脚本。试点反馈可以改变字段和表的组织方式，但不能让已发送的推荐、答复和 RFQ 失去当时依据。无需等界面雏形做好后才首次设计数据库，也无需现在冻结所有物理表。

| 时点 | 要完成的事 | 暂不固定的事 |
| --- | --- | --- |
| 功能开发前 | 核心对象、企业隔离、产品事实来源、版本及快照关系 | 数据库品牌、所有表名与索引 |
| 逐条用户旅程开发时 | 为该流程建立最小表结构、约束和版本化迁移；用样例数据走通读写 | 未来营销、CRM、支付等功能的数据表 |
| 小范围试点后 | 根据真实缺字段、查询和数据质量问题做迁移；保留历史映射 | 无依据地一次性重建全库 |

## 2. MVP 最小逻辑对象

这里的“对象”不等于“一对象一张表”；开发时可合并或拆分，但关系必须可追踪。

| 对象 | 关键关系与必须保留的信息 |
| --- | --- |
| 企业、成员 | 企业是后台数据的归属边界；成员操作记录企业、操作者和时间。公开页的访问权限另行控制。 |
| 产品/型号、来源资料 | 型号属于企业；原手册、CAD 和其他附件记录来源、文件版本、权限及所属型号。新上传不覆盖旧文件。 |
| 核准产品事实/产品版本 | 技术字段保留数值、单位、出处及核准状态；发布后形成可引用的产品版本。提取草稿与核准事实分开。 |
| 产品详情页版本 | 页面引用某个已核准产品版本；页面发布或撤回有状态和时间。页面排版不成为第二套技术参数。 |
| 会话、消息、需求修订 | 消息保留原文和来源；需求区分 AI 提取候选、买方/销售确认值、未知项；每次更正形成可追踪修订。 |
| 推荐 | 记录当时的需求修订、候选产品版本、匹配规则/依据、冲突和未知项；发给买方后仍能复现理由。 |
| 问答、引用、人工任务 | 回答关联会话、所用产品版本及具体出处；无可靠依据时创建人工任务。工程师的单次答复不自动变成通用产品事实。 |
| RFQ、线索、跟进 | RFQ 保存提交时的需求和推荐快照、联系人及缺失项；线索关联负责人、处理状态与跟进记录。 |

一条关键追踪链是：`企业 → 产品版本 ← 来源资料`；`会话 → 需求修订 → 推荐 → 产品版本/详情页版本 → 问答或人工任务 → RFQ/线索`。同一客户可有多次需求修订，产品也可有多个版本，因此不应只保存“当前值”。

## 3. 比表名更早要定的规则

1. **企业隔离**：企业私有对象和查询都有可信的企业归属；不能仅依靠前端传入的 `tenantId` 限制访问。买方公开链接与企业后台权限分开。
2. **出处与核准**：参数值要能追到来源资料与核准记录；AI 抽取结果不能直接作为已核准产品事实。
3. **版本与快照**：产品更新后，旧页面、推荐、回答和 RFQ 仍可追到当时使用的版本；更正以新修订表示。
4. **单位与可匹配字段**：流量、扬程、功率等选型关键量应有明确类型和单位，不能全部藏在自由文本中。不同产品类别的扩展参数可逐步定义，不必现在把所有工业品参数做成固定列。
5. **幂等与操作历史**：外部消息或 RFQ 重试提交应有去重依据；发布、核准、转人工及处理状态变化保留操作者和时间。
6. **地域含义分开**：`tenantId` 是企业归属；卖方市场、买方语言/地区和数据部署地域各自表达不同问题。海外版本的数据物理隔离方案须在海外公开测试前单独确定。

## 4. 现在不预建的部分

暂不为 SEO 批量内容、营销序列、CRM 双向同步、支付或自动 CAD 建模设计完整物理表。仅保留现有对象的稳定 ID、版本、来源和必要状态，供未来扩展。也不先把所有字段塞进单个 JSON 文档：那会使筛选、单位校验、来源追溯和版本比较变得困难。

## 5. 开发与验收检查

- 每个功能切片提交数据库迁移脚本；用已有试点样例验证迁移后历史记录仍可读。
- 用两个企业的数据验证私有产品资料、会话、RFQ、文件及检索结果不能串读。
- 更新产品资料后，能展示旧 RFQ 当时引用的参数和来源；不会静默变成最新版。
- 同一询盘或 RFQ 重试不会生成重复业务记录；缺证据的问答能关联到人工任务。
- 首次使用真实试点数据前，完成数据库和关键文件的备份恢复演练；要求见 [架构决策记录](架构决策记录.md)。

## 6. M3/M4 当前实现细化（2026-10-02）

第二个应用切片已将以下逻辑对象落到 SQLite；表名是当前实现选择，后续迁移可调整，但追踪关系不能丢失：

| 当前表 | 保留内容 | 关键约束 |
| --- | --- | --- |
| `conversations` | 企业归属、来源、界面语言、状态和时间 | 所有消息与需求修订必须带会话 ID 和企业 ID |
| `messages` | 买方原话、角色、来源、时间 | 原话只追加不覆盖；结构化提取不能替代原文 |
| `requirement_revisions` | 修订序号、字段值、字段状态、来源、缺失字段和确认时间 | 候选值与买方确认值分开；每次确认/更正形成新修订 |
| `recommendations` | 需求修订 ID、状态、规则版本、候选结果、满足/冲突/未知项和生成时间 | 新推荐会使同一会话的旧推荐失效；结果保存产品版本 ID 和详情页链接 |

当前 `pump-demo-v1` 规则只读取已确认的流量、扬程、介质（缺任一项则为“条件不足”）和已发布产品版本。该规则是演示规则，不是企业正式选型阈值；正式阈值确认后再替换规则版本并保留旧结果。

M5 新增 `answers` 和 `human_tasks`：答案保存问题消息、产品版本、回答状态和引用；人工任务保存原问题、需求修订、推荐、型号、已有回答、转人工原因、状态和工程师回复。工程师回复属于当前会话，不能直接写入 `product_fields` 或新的产品版本。

M6 新增 `rfqs` 和 `leads`：RFQ 保存提交幂等键、联系人、询价字段、缺失项、状态及提交时的需求/推荐/产品版本快照；同一企业重复提交同一幂等键返回已有记录。`leads` 先保存 `new` 或 `needs_info` 阶段，为 M7 的负责人、阶段和跟进记录提供稳定关联。M7 更新 `leads` 时写入操作者和时间到操作记录；负责人、阶段、跟进日期和备注不改写 RFQ 的历史快照。

管理端认证切片新增 `users` 和 `sessions`：用户有企业归属、角色和密码哈希；会话保存用户、企业和过期时间，后台查询从会话取得 `tenant_id`，不信任前端传入企业 ID。当前只种入本地演示账号，正式身份提供商、密码重置、多因素认证和管理员账号管理暂不在本切片内。

**下一步**：在 M3/M4 验证基础上实现 M5 有据问答与人工任务，再按实际流程扩展 RFQ 和销售跟进对象。具体数据库产品、索引和完整 SQL schema 留给实现与测试决定。
