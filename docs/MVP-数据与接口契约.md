## 1. 一条旅程只用一组权威对象

```text
tenant ─ product ─ approved product_version ─ published page_version
              └ source_asset / fact_draft / approved_fact

tenant ─ conversation ─ original_message ─ requirement_revision
                         ├ recommendation_run ─ product_version + page_version
                         ├ answer / unresolved_question ─ human_task ─ delivered_message
                         └ lead ─ rfq ─ rfq_revision ─ confirmed_contact
```

| 稳定 ID | 谁产生/归属 | 关键约束 |
| --- | --- | --- |
| `tenant_id`、`member_id` | 卖家身份层 | 企业归属只由服务端登录态或已注册的网站接入配置确定；买方请求中的企业 ID 不可信。 |
| `product_id`、`product_version_id`、`page_version_id` | 产品知识及发布 | 型号身份稳定；批准/发布后的内容不可原地覆写。页面、匹配、问答只读当时核准事实；撤回版本不能用于新的肯定性回答或推荐。 |
| `source_asset_id`、`fact_id` | 产品知识 | 技术主张必须能定位文件、版次、页码/位置、系列或型号范围及核准状态；文件可公开使用许可单列。 |
| `conversation_id`、`message_id` | 买方会话 | 原话只追加；产品页 URL 本身不授予读取私人会话的权利。直接访客也可在需要提问/询价时建立新会话。 |
| `requirement_revision_id` | 买方需求 | 草稿、买方确认值和明确未知项分开；更正新建修订，旧推荐失效。 |
| `recommendation_run_id` | 匹配 | 记录所用已确认需求修订、规则版次、产品与页面版次、满足/冲突/未知理由及买方所见标签；已知型号直访不伪造推荐。 |
| `unresolved_question_id`、`human_task_id` | 问答/人工 | 未解问题可存在而无任务；买方显式提交请求才建任务。草稿与已送达人工答复分开。 |
| `lead_id`、`rfq_id`、`rfq_revision_id` | 销售/询价 | 同一网页会话一个线索负责人、可有多份独立 RFQ；原采购请求的修改增加修订，不换 RFQ 编号。初次提交和每次修改仅卖方看历史，买方只看当前值。 |

当前 Python/SQLite 测试应用已有部分同名对象，但字段、访问控制和历史行为与此契约并不完全一致；差异见[代码核查与复用决策](现有代码核查与复用决策.md)。按切片做迁移，不在同一补丁一次创建全部未来表。

## 2. 买方聊天 API 的调用边界

企业官网可自建聊天前端；参考客户端也只调用同一 API，不直读数据库。公开产品页与买方聊天可以有不同的展示形态，不能形成各自一套产品事实或 RFQ 表。

**身份提案，须在实现前进行安全审查**：企业获得一个可公开的网站接入标识，服务端用它找到企业及允许的官网来源；该标识不等于私钥，也不授予后台权限。新会话产生随机、不可猜测的访问凭据，服务端只存其摘要；读取或修改会话、RFQ 时同时校验凭据与企业归属。参考客户端在同一浏览器保存该凭据以便返回原会话；清除站点数据或换设备后不能仅凭会话 ID、产品链接或同一邮箱找回。企业服务端接入如需私钥，私钥只能保存在其服务器。跨站浏览器接入的来源白名单、凭据存储、过期与刷新方式需在联调时定型，不能把 `Origin` 检查当成唯一身份认证。

下表是**外部买方**的最小 v1 资源契约。所有写入请求接受 `Idempotency-Key`；同一作用域、同一键及同一内容重试返回原结果，改内容用同一键返回冲突。客户端新业务动作必须产生新键；不能用问题文本或买方邮箱去重。

| 操作 | 建议路径/方法 | 输入与返回重点 | 界面验收 |
| --- | --- | --- | --- |
| 开始会话 | `POST /api/v1/buyer/conversations` | 网站接入标识、语言、入口来源 → 会话 ID、访问凭据、当前状态 | 不登录即可开始；没有后台成员权限。 |
| 恢复/读取 | `GET /api/v1/buyer/conversations/{id}` | 有效会话凭据 → 允许买方看的消息、需求当前修订、任务状态及自己的 RFQ 当前值 | 刷新后可续；无凭据不泄露旧会话。 |
| 发送原话 | `POST /api/v1/buyer/conversations/{id}/messages` | 原文、客户端消息 ID → 消息 ID、提取草稿与最关键的待确认项 | 原话保存；模型失败仍有可见失败/人工路径，不能假装已识别。 |
| 更正并确认需求 | `POST /api/v1/buyer/conversations/{id}/requirements/confirm` | 已知值含单位、未知项、所依据的草稿/上一修订 → 新需求修订 ID | 未确认前不返回匹配候选；更正令旧结果失效。 |
| 取得匹配结果 | `POST /api/v1/buyer/conversations/{id}/recommendations` | 已确认需求修订 ID → 候选、待核实候选或无可靠候选，含理由、冲突、缺项、规则及产品/页面版次 | 待核实候选须买方选择查看；硬冲突和无技术依据不输出为适用候选。 |
| 提问 | `POST /api/v1/buyer/conversations/{id}/questions` | 问题、可选产品/页面上下文 → 有出处答案，或未解问题 ID 与需核实点 | 未解问题不自动产生人工任务；出处可定位。 |
| 请求人工 | `POST /api/v1/buyer/conversations/{id}/human-requests` | 未解问题 ID、回复路径（原会话或已确认联系方式） → 任务 ID、真实创建/排队状态 | 取消不请求；重复点击不建多任务。 |
| 提交 RFQ | `POST /api/v1/buyer/conversations/{id}/rfqs` | 可空的型号/工况/数量、至少一种已确认可回复方式、来源界面 → RFQ ID、当前修订、缺项、处理状态 | 任意阶段可发；不因缺技术条件拒收；无确认联系方式时阻止提交。 |
| 修改原 RFQ | `POST /api/v1/buyer/conversations/{id}/rfqs/{rfq_id}/revisions` | 期望当前修订号、修改后的当前内容及确认联系方式 → 同一 RFQ ID、新修订号 | 买方只读当前值；卖方可见原内容与差异；并发旧版本返回冲突供重载。 |
| 读取公开页 | `GET /api/v1/public/products/{slug}` | 已发布、未撤回的页面版次和公开字段/素材 → 固定页面数据 | 只读公开内容；无会话凭据也可访问；不能泄露上一买家工况。 |
| 出具跨站交接码 | `POST /api/v1/buyer/conversations/{id}/handoff-codes` | 会话凭据 + 已登记来源 + 已发布型号 → 一次性交接码（默认 10 分钟有效，服务端只存摘要） | 原官网聊天为产品链接领取交接码；未发布/跨企业型号 404；来源不符 403；用户不可见长期凭据。 |
| 兑换跨站交接码 | `POST /api/v1/buyer/handoff/exchange` | `X-Site-Key` + 交接码 + 型号（仅平台自身页面来源）→ 同一会话的新访问凭据 | 一次性、短时、绑定企业/网站标识/型号；失败不发凭据；陌生来源不留跨域放行头；长期凭据不出现在 URL。 |

**与卖家系统的关系**：核准、发布、撤回、人工答复、RFQ 领取与分配使用后台登录/角色权限，不用买方凭据执行。人工答复先持久化并成功交付原会话后，买方读取才显示“已答复”；发送失败保留草稿/待重试状态。具体卖家端 URL 可沿用现有页面路由并逐切片调整，无需额外部署一个服务。

## 3. 跨端状态与失败语义

- **版本**：产品补资料后产生新 `product_version` 和 `page_version`；旧推荐、答复、RFQ 保留当时 ID 与必要快照。公开链接可指最新已发布页，历史对象仍能追到其原版本。买方改工况只使当前推荐失效，不删历史。
- **幂等**：消息、人工请求、RFQ 提交与修订都要抗网络重试。RFQ 初次提交、首个修订、确认联系方式和进入共享队列须同一事务完成；相同键不同请求内容返回 `409`，不能暗中合并两个独立采购意图。
- **权限**：后台读写以已认证成员的企业和权限过滤；买方以会话凭据访问自身私有数据；公开页只给公开信息。私有文件下载再检查企业和许可，不把对象存储路径当公开 URL。
- **错误**：无效字段返回 `422` 且标明字段；无/失效凭据返回 `401`，无权限为 `403`，对象不存在或跨企业不可见可统一为 `404`；修订冲突 `409`；限流 `429`；模型或依赖不可用 `503` 并返回可继续的会话状态。所有失败都不得宣称已经发布、答复送达或 RFQ 已提交。
- **语言和来源**：后台默认中文、买方默认英文，可切换而不清空业务输入。原始技术引用保持文件原语言；`seller_market`、`buyer_locale`、`data_region` 是三种不同字段/配置。
- **双入口 RFQ**：项目负责人已确认详情页底部表单直接提交询盘，原官网聊天窗口也可随时提交；两者调用同一 RFQ API，分别记录 `entry_surface=product_page` 或 `chat`，不复制“页面专用询盘表”。从已有会话打开的产品页须安全地带回该会话上下文；直访者按 API 建立自己的会话。跨站会话交接采用一次性交接码（见 §3.1），长期访问凭据不放进可分享的公开 URL。

### 3.1 跨站会话交接（一次性交接码；2026-10-03 确定并实现）

企业官网聊天（来源 A）与平台产品页（来源 B）分属不同浏览器来源时，按以下信任边界接续同一会话：

- **出具**：来源 A 的聊天凭会话凭据 + 已登记来源调用 `POST /api/v1/buyer/conversations/{id}/handoff-codes`（body 为型号），得到一次性交接码。码随机 256 位、服务端只存 SHA-256 摘要、默认 10 分钟有效、单次使用、绑定「企业、网站标识、会话、型号」四项；每会话只保留最近若干码与交接凭据（防无上限增长，数值见 `app.py` 常量）。
- **传递**：码只经 URL fragment（`…/products/{slug}#handoff=<码>`）交给来源 B 的产品页；fragment 不发送给服务器、不进入访问日志与 Referer，页面读取后立即用 `history.replaceState` 从地址栏清除；公开产品页附 `no-referrer` 策略。**长期会话凭据从不进入 URL、日志、公开 HTML 或 Referer。**
- **兑换**：来源 B 的产品页在平台自身来源上（请求 `Origin` 存在时须与 `Host` 同源）调用 `POST /api/v1/buyer/handoff/exchange`，服务端在同一写事务内原子消费该码并签发**同一会话的新凭据**，写入来源 B 浏览器存储。原聊天持有的凭据继续有效（同会话多凭据，互不撤销）；页面 RFQ 因此直接写入原会话（`entry_surface=product_page`），原聊天刷新与卖家企业队列均可见。同源部署下同一机制生效，并与既有 localStorage 会话兼容。
- **来源边界**：兑换接口永不返回跨域放行头；带陌生 `Origin` 的请求 403 且**拒绝不消费交接码**。出具接口沿用网站来源白名单（登记来源或同主机页面）。
- **失败语义（不发放凭据、不接回旧会话、不按邮箱/会话 ID 关联）**：未知码 404 `handoff_not_found`；绑定不符（跨企业、未发布、已撤回型号、站点不符）403 `handoff_binding_mismatch`；重放 409 `handoff_already_used`；过期 410 `handoff_expired`；陌生来源 403 `origin_not_allowed`。产品页显示明确提示，该标签页按独立新访客处理：不读取、不复用任何已存会话，提交时建立自己的新会话（只存本标签页）。失败交接页同时作废本标签页此前的成功固定凭据，刷新后继续按独立新访客处理。
- **标签页归属（2026-10-03 修复串单缺陷时修订）**：成功交接把凭据固定到打开它的标签页（页面 sessionStorage），提交只读本标签页凭据，并照旧更新浏览器级保存会话（localStorage，同源部署与后续无码直访复用）；同一站点另一标签页随后的成功交接只影响它自己和浏览器级保存会话，不改变本页已接回的会话归属；成功交接标签页刷新后仍固定原会话（不重新兑换）。无码直访保持既有行为（优先复用浏览器保存的会话，否则提交时新建），但已绑定（成功或失败交接）的标签页永不回落该共享会话。连续失败交接的复用范围核算为仅限同一标签页自身的独立会话，不同标签页之间不共享。
- **边界说明**：直访者（无码、无已存凭据）照常建立自己的会话；清除站点数据、关闭标签页后重开或换设备后仍不恢复匿名会话（沿用 §3 规则；标签页级固定凭据随标签页关闭消失）；凭据过期/轮换与正式外部官网部署、安全评审待试点阶段联调。

## 4. 首批真实切片如何验证本契约

1. 用两个企业分别建产品、会话和 RFQ；服务端拒绝跨企业 ID、文件和会话访问，而不是仅隐藏按钮。
2. 让一个产品发布 v1、发送推荐、提交 RFQ；更新并发布 v2 后，旧推荐和 RFQ 仍返回 v1 的依据，新问答只用允许使用的当前版本。
3. 发送需求草稿、确认后才取得候选；修改后旧结果标失效；无核准相关性或有硬冲突不进入候选。
4. 同一提交键重试消息、人工请求、RFQ 和修订，记录数不增加；RFQ 初次提交没有联系方式时不创建部分记录。
5. 从参考网页聊天调用 API：打开详情页新标签后原聊天仍在；刷新可用凭据继续，清除凭据后不能靠公开链接或已知会话 ID 读取私有数据。
6. 工程师回复失败时买方仍见待处理；成功后原会话出现有人工身份的消息。重启应用后产品、消息、任务与 RFQ 不丢失。

验收以实际 API 响应、数据库状态和界面点击为准；本文只是建立共同语言，不能把接口设计当实现完成。

## 5. 当前实现状态（2026-10-03）

已由代码和 HTTP 测试覆盖：登记网站标识与允许来源的数据库对象；`POST /api/v1/buyer/conversations`、`GET /api/v1/buyer/conversations/{id}`、`POST .../messages`、`POST .../requirements/confirm`、`POST .../recommendations`、`POST .../questions`、`POST .../human-requests`、`POST .../rfqs`、`POST .../rfqs/{rfq_id}/revisions`。API 使用网站标识确定企业，以每会话随机凭据访问私有对象；会话读取返回当前需求、推荐、问答、任务和 RFQ 当前值。推荐目前沿用明确标为演示的水泵规则；RFQ 初次提交要求联系信息和确认标记，同一提交键的相同内容重试不重复建单，改内容返回冲突。RFQ 修订沿用原编号，以期望版本号处理过期修改；初次提交和修订只在卖方 RFQ 详情显示历史，测试证明重开数据库后仍在。
