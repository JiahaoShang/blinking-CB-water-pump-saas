# 平台核心功能拆解与两人分工

## 1. 先澄清三个概念

### 1.1 用户画像是什么

用户画像不是一张销售名单，也不是一段 AI 总结，而是平台保存的买方事实和需求状态。它至少包括：

- 基本信息：姓名、公司、国家/地区、联系方式、买方角色；
- 需求信息：产品品类、用途、流量、扬程、介质、温度、数量、目的地、期望交期；
- 可信状态：买方已确认、AI 提取候选、销售修正、未知/待补充；
- 来源和时间：来自哪条消息、哪次表单、何时确认；
- 行为上下文：看过的产品、问过的问题、提交过的 RFQ、是否转人工。

画像的核心原则是：每个用于匹配或报价判断的值，都能回到买方输入、确认动作或销售修改记录。

### 1.2 销售工作台是什么

销售工作台是企业内部的工作界面，不是另一份用户画像。它读取用户画像，并在其上增加销售处理信息：

- 线索列表和优先级；
- 负责人；
- 当前阶段；
- 待补充字段和技术任务；
- 跟进日期、下一步和备注；
- 产品推荐、问答、RFQ 和操作时间线。

关系可以理解为：

```text
买方消息/表单
      ↓
用户画像与需求修订（数据对象）
      ↓
推荐、问答、RFQ、人工任务
      ↓
销售工作台（销售查看、分配、跟进的界面）
```

销售工作台必须能看到用户画像，但不能直接修改原始买方消息；销售对画像的修正要留下操作者和时间。

### 1.3 API 是什么

API 是页面和后端之间约定好的数据入口。页面不应该直接读数据库，而是通过 API 完成读取和保存。

例如：

| 页面动作 | API 做的事 |
| --- | --- |
| 买方发送一条消息 | 保存消息，提取/更新画像，返回下一步追问 |
| 买方确认需求摘要 | 保存新的需求修订，触发推荐 |
| 销售打开线索 | 读取画像、推荐、问答、RFQ 和时间线 |
| 销售修改负责人 | 保存负责人和操作记录 |
| 买方提交 RFQ | 校验字段、保存 RFQ 快照、创建销售线索 |

API 是 B 负责实现的程序接口；A 负责规定这些接口里的业务字段、状态和判断规则。两人不应该各自设计一套互不兼容的数据结构。

## 2. 两天内必须做出的核心闭环

两天结束时只验收下面这条路径：

1. 系统中有两款适用条件不同的示例水泵；
2. 买方在聊天页面输入用途、流量和扬程；
3. 页面显示用户画像/需求摘要，并区分已确认、待确认和未知；
4. 买方补充或确认关键条件；
5. 系统按固定规则给出推荐、理由、冲突项和未知项；
6. 买方查看产品详情并提问；
7. 资料内问题显示答案和来源，资料外问题创建人工任务；
8. 买方提交 RFQ；
9. 销售工作台显示这条线索的画像、推荐、问答、RFQ 和下一步；
10. 销售可以分配负责人、修改阶段、设置跟进日期并留下备注；
11. 刷新页面后数据仍然存在。

## 3. 按模块拆解，而不是按“AI/前端”笼统拆分

### M0 共享数据契约

这是两人开始编码前必须共同确定的部分。

| 内容 | 最小字段 |
| --- | --- |
| 产品 | `productId`、型号、名称、状态、企业 ID |
| 产品版本 | `productVersionId`、产品 ID、版本号、核准状态、核准时间 |
| 产品字段 | 字段名、数值、单位、适用条件、来源位置、核准状态 |
| 会话 | `conversationId`、来源、状态、创建时间 |
| 消息 | `messageId`、会话 ID、角色、原文、时间 |
| 用户画像 | 会话 ID、字段名、候选值、确认值、状态、来源消息 ID |
| 需求修订 | `requirementRevisionId`、已确认字段、未知字段、修订时间 |
| 推荐 | `recommendationId`、需求修订 ID、产品版本 ID、结果、理由、冲突项、未知项 |
| 问答 | 问题、答案、引用、产品版本 ID、是否转人工 |
| 人工任务 | `taskId`、问题、上下文、负责人、状态、回复 |
| RFQ | `rfqId`、需求快照、产品版本、联系人、数量、目的地、交期、缺失项 |
| 销售线索 | RFQ/会话 ID、负责人、阶段、跟进日期、备注、更新时间 |

**共同完成标准**：A 提供业务字段和状态，B 将其写成共享类型/数据库 schema；页面、API、规则和测试使用同一命名。

### M1 产品资料与产品页

**用户要完成的事**：管理员准备两款产品，确认参数，发布产品页。

**A 负责**：

- 两款水泵的示例数据；
- 流量、扬程、介质等字段的单位和来源；
- 哪些字段可以公开；
- 哪些字段必须核准；
- 产品详情页的中英文内容和边界提示；
- 产品匹配需要读取哪些已核准字段。

**B 负责**：

- 产品列表页；
- 产品详情编辑/核准/发布状态；
- 产品版本保存；
- 产品详情公开页；
- 产品字段和来源位置的展示；
- 两款产品的种子数据导入。

**两天最小实现**：先使用种子 JSON/数据库脚本，不做 PDF 自动解析；页面必须能展示来源和版本。后续再补真实文件上传和抽取。

### M2 买方聊天与用户画像

**用户要完成的事**：买方聊天，系统逐步收集和确认画像。

**A 负责**：

- 画像字段清单；
- 每个字段的状态定义；
- 关键追问顺序；
- 10 条中英文测试输入；
- 买方拒答或信息不足时的处理规则；
- 聊天摘要中的产品事实边界。

**B 负责**：

- 买方聊天页面；
- 消息保存 API；
- 画像摘要卡；
- 已确认/待确认/未知的显示；
- 买方确认和修改动作；
- 会话刷新后的恢复。

**两天最小实现**：先支持水泵固定字段；需求提取可以用规则解析或模型适配器，但必须保存原话，不能只保存模型总结。

### M3 匹配与推荐

**用户要完成的事**：根据已确认画像得到可解释结果。

**A 负责**：

- 匹配字段和示例阈值；
- “可初步推荐 / 条件不足 / 无可靠候选”的判断；
- 满足项、冲突项、未知项的计算规则；
- 至少 6 个正例和反例；
- 推荐文案和不确定性提示。

**B 负责**：

- 匹配 API；
- 推荐结果保存；
- 推荐卡页面；
- 产品详情页跳转；
- 需求修改后重新计算；
- 旧推荐标记失效。

**两天最小实现**：使用确定性规则，不让 chatbot 自己判断硬条件；规则版本写入推荐记录。

### M4 Chatbot 问答与人工接管

**用户要完成的事**：得到有资料依据的答案，无法确认时交给人。

**A 负责**：

- 5 个资料内问题及期望答案；
- 5 个资料外/工程判断问题；
- 每个资料内答案的引用位置；
- 禁止编造的内容清单；
- 人工任务需要看到的上下文；
- 人工答复是否只对当前会话有效。

**B 负责**：

- chatbot 调用 API/模型适配器；
- 输入产品版本和相关资料；
- 保存答案和引用；
- 超时/失败时保留问题；
- 资料不足时创建人工任务；
- 买方侧状态提示和后台任务页面。

**两天最小实现**：先用结构化产品知识和受控问答；模型不可用时必须仍能创建人工任务。不要在两天内建设复杂向量数据库。

### M5 RFQ 与销售线索

**用户要完成的事**：买方提交询价，销售接手并跟进。

**A 负责**：

- RFQ 必填字段和“待补充”规则；
- 线索阶段定义；
- 可报价和待补充的区别；
- 销售必须看到的画像字段；
- 下一步动作模板。

**B 负责**：

- RFQ 表单和预填；
- 提交前摘要；
- RFQ 唯一 ID 和重复提交保护；
- 线索自动创建；
- 销售线索列表、详情和时间线；
- 负责人、阶段、跟进日期、备注的保存。

**两天最小实现**：销售工作台只做线索列表、线索详情和状态更新，不做 CRM、报表和自动跟进。

## 4. 分支和代码边界

建议把原来的分支名改得更贴近工作内容：

```text
main                         可演示稳定版本
├── feat/domain-rules         A：字段、产品数据、匹配规则、问答测试
└── feat/app-flow             B：页面、API、数据库、会话、RFQ、销售工作台
```

### A 的代码/文件边界

- `data/demo-products.*`：两款水泵和来源信息；
- `packages/domain` 或 `src/domain`：字段 schema、状态枚举、匹配规则；
- `tests/fixtures`：聊天、匹配、问答验收样例；
- `docs/`：字段字典、规则和验收说明。

A 不直接改 B 的页面组件和数据库迁移；如果字段需要变更，先更新共享 schema 和测试。

### B 的代码/文件边界

- `apps/web` 或 `src/app`：页面、组件、表单和导航；
- `apps/api` 或 `src/server`：API、权限、业务编排；
- `prisma/`、`db/` 或等价目录：数据库模型和迁移；
- `tests/api`：接口和持久化测试。

B 不在页面里复制一份产品参数或匹配规则；所有业务事实通过共享数据和 API 读取。

### 共同修改的文件

共享 schema、数据库模型和接口类型属于高冲突文件。修改前在群里说明字段、状态或关系变化，修改后当天合并，不留到最后一小时才解决冲突。

## 5. 两天按半天执行

### 第一天上午：定契约，做数据和骨架

**A**：

- 完成两款水泵数据；
- 完成画像字段和状态；
- 完成匹配规则和测试案例；
- 完成问答测试集初稿。

**B**：

- 拉取 GitHub 仓库并创建分支；
- 确定应用启动方式；
- 建数据库 schema 和种子加载；
- 建会话/消息/画像/推荐/RFQ/线索的最小 API 骨架。

**共同关卡**：用 30 分钟对照字段表，确认名字、单位、状态和 ID 一致。

### 第一天下午：打通“聊天 → 画像 → 推荐 → 产品页”

**A**：

- 完成画像提取/确认规则；
- 完成推荐判断函数；
- 用正例、反例验证推荐结果；
- 审核产品页的参数和推荐理由。

**B**：

- 完成买方聊天页面；
- 完成需求摘要卡和确认动作；
- 完成推荐 API 和推荐卡；
- 完成产品详情页链接。

**第一天结束必须演示**：输入“需要某流量和扬程的水泵”，页面保存原话，显示画像，补充确认后出现推荐。

### 第二天上午：打通“问答 → 人工任务 → RFQ”

**A**：

- 完成资料内/资料外问答测试；
- 确认引用和无法确认文案；
- 确认 RFQ 字段、缺失项和线索阶段；
- 准备最终验收脚本。

**B**：

- 完成 chatbot 适配和引用展示；
- 完成资料外问题的人工任务；
- 完成 RFQ 表单、快照和幂等提交；
- 把 RFQ 自动转换为销售线索。

**第二天中午必须演示**：一个问题得到引用答案，另一个问题进入人工任务，随后提交 RFQ。

### 第二天下午：销售工作台、联调和交付

**A**：

- 从买方视角完整走主路径；
- 检查画像是否准确、推荐是否有依据、引用是否正确；
- 检查销售页面是否能理解买方背景；
- 记录阻断问题和延期问题。

**B**：

- 完成销售工作台列表/详情/状态更新；
- 完成刷新恢复、错误提示和最小权限检查；
- 修复主路径阻断问题；
- 准备启动和演示说明。

**最终关卡**：不运行脚本、不改数据库、不依赖开发聊天，只用网页界面完成完整主路径。

## 6. 两天内明确延期的内容

- 任意 PDF/Excel/CAD 自动解析；
- 多品类通用产品模型；
- 复杂权限后台和多组织管理；
- 复杂向量检索、知识图谱和模型路由；
- 真实外部消息渠道；
- CRM 同步、自动营销、价格库存和自动报价；
- 完整备份恢复演练、监控平台和多地域部署；
- 高保真视觉打磨和 SEO 批量页面。

延期不是删除需求，而是保证两天时间用于核心业务闭环。演示时必须标明“本轮为可运行 MVP 垂直切片”。

## 7. 最终完成定义

只有满足以下条件，才称为“两天切片完成”：

- 两款产品数据已保存，并有版本/来源信息；
- 买方原话、画像字段和确认状态都能回看；
- 推荐结果能复现，且展示理由/冲突/未知；
- 资料内问题有引用，资料外问题生成任务；
- RFQ 有唯一记录且重复提交不重复创建；
- 销售工作台能看完整画像和会话上下文，并能更新负责人、阶段和跟进日期；
- 刷新页面后数据仍在；
- A 和 B 共同完成至少一次主路径和三次异常路径验收；
- 未完成的上传、权限、模型和部署能力被明确标记为延期，不冒充已完成。
