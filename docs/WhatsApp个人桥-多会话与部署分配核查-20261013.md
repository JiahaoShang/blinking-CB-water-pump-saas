## 当前项目实际实现与缺口

- business_channels.py 为每条新个人桥连接创建 business-<24位账号ID> 会话名及独立 webhook_token；成员管理与业务记录按企业/账号关联。
- channel_runtime.py 有 WHATSAPP_PERSONAL_MULTI_SESSION=1 分支，跳过 Docker 创建；否则每账号容器使用 default 会话。
- app.py 回调核对独立令牌及 session，发送/扫码按连接 session；这些是多会话接入基础。
- 目前桥接 API Key 是平台环境变量；WHATSAPP_PERSONAL_BASE 全局地址通常优先于账号地址。因此多容器按企业分配、独立密钥、桥节点分配还不是已完成的产品能力。
- 当前备份停止逻辑只识别 connection-runtime 下24位账号目录和 b2b-account-<ID> 容器；共享桥或企业桥须调整停写、卷路径、恢复验证，不能只打开开关。
- 云端准备镜像 noweb-2026.9.2 已拉取，确认 amd64；未开展该镜像真实多会话联调。
- 独立执行 python3 -m unittest test_channel_runtime test_business_channels -q：34项通过；包含模拟传输/容器测试，不是 WhatsApp 实机或共享桥跨企业验收。

## 分配与成本建议（未采纳）

账号数与 session 数对应，成员数不增加 session。容器内会话的具体上限应按实测确定，不能用官方 unlimited 推断4GB容量。

1. 每账号容器：N个账号/N个容器，重复程序内存较多；容器间隔离更强，但仍共享同一服务器。
2. 所有企业共享桥：N个账号/N个session/1个容器，重复开销最少；运行资源与故障影响共享，必须有严格平台权限、按session路由、独立回调及公平资源策略。
3. 每企业一个多会话容器：有WhatsApp账号的T个企业通常T个容器，每企业容器内账号数=该企业已绑定号码数；大企业超过实测限额才拆分。保留企业容器/卷/密钥边界，降低每账号容器的重复开销。当前代码仍需最小适配，不能称现成可用。

例：A企业3账号、B企业2账号、C企业1账号，分别为6/1/3个容器，三种模式都需要6个session。该例不是4GB承载承诺。

建议先1个试点企业使用1个运营预部署的NOWEB多会话容器；多企业时优先评估按企业分配，不默认跨企业共用。不授予应用Docker管理权限，仅用桥接HTTP接口执行账号会话操作。是否采纳待用户决定。

两种账号容器模式的WAHA必需授权费都为0；同一台服务器内容器数增加不会自动产生按容器账单。差异是重复运行开销、容量升级时机、运维成本；账号消息量决定的磁盘、网络、备份与AI费用不因合并容器消失。相同Docker镜像层可复用，不能按每容器重复计算整个镜像容量。

必要验收：两个测试企业与多个明确测试账号的入站/原账号回复、成员撤权、错误session回调拒绝、断开互不影响、重启与备份恢复；增加活跃账号时测内存CPU峰值、消息延迟、发送积压及备份耗时。外部授权/发送需针对性授权。未承诺月度节省金额或最大账号数。

## 2026-10-14 用户决定与执行边界

用户明确选择每企业一个多会话容器，先部署当前pilot-t4，必要适配、验证多账号连接/消息分流/资源/备份恢复；不授予应用Docker权限。已有两个可用测试WhatsApp账号，并授权两者相互发送带T4/T5测试标记的文本。采用运营root部署企业桥，应用仅HTTP会话操作；缺企业注册表配置时拒绝而不回退其他桥。每企业私有密钥、每账号独立会话与回调令牌；挂载登录状态和媒体目录，快照前停写企业桥，失败恢复原状态。现有界面不改交互。首批只pilot-t4；不自动采购、扩容、公开发布或启用AI。
