# 开发状态与变更记录

**用途**：区分“文档计划了什么”和“本仓库实际完成了什么”，并记录影响范围的决定。文档不会因代码变化或时间经过自行更新；开发任务结束时应由执行者核对代码、验收结果并更新本页。完整的文字修改历史由 Git 提交保存。

## 状态定义

| 状态 | 含义 |
| --- | --- |
| 未开始 | 当前仓库没有该功能的可验证实现 |
| 开发中 | 已有实现工作，但尚未通过对应验收 |
| 已验证 | 在当前仓库通过对应文档的验收，并留下测试或演示证据 |
| 已上线 | 已部署到明确环境，并确认该环境中的功能可用 |

**限制**：页面原型、外部 Demo、需求文档和代码草稿不等于“已验证”。状态只描述本仓库及指定环境；如果后来发现回归缺陷，应记录新的状态和原因，不静默保留“已验证”。

### MVP 用户旅程与交互评审（2026-10-01，进行中）

**来源**：本轮用户提出的体验评审请求；核对当前 MVP 第 1、3、5、6 节及技术架构的数据与隐私边界。本仓库仍只有规划文档，没有可操作产品或真实买家使用证据；下列内容属于设计评审假设，不是测得的流失或效率结果。

**应保留的已有设计**：核准事实与来源引用、可复用产品页、需求可纠正与未知项标记、RFQ 预填、人工任务携带上下文，以及销售集中查看记录。这些要求已经写入 MVP，不因本轮讨论重复新增功能。

**待评估的旅程细节**：

- 企业首次使用：明确发布第一张有用产品页所需的最小资料与核准项，以及抽取失败/媒体缺失时如何继续；不能为了缩短流程取消关键事实审核。
- 买家入口：已确认已知型号者可直接查看、提问和询价，无需完整重走需求匹配；仍需评审从页内提问到人工答复的返回路径。
- 需求交互：已确认对话结合可编辑参数卡；仍需细化追问停止条件，以及买家标记“不确定”后的下一步。
- 详情页层级：已有参数、曲线、图纸和 3D 分区；待讨论首屏如何帮助买家判断用途/初步适配与下一步，详细资料按需展开。通用分享链接不得包含另一位买家的推荐理由或私人数据。
- 人工接管：已确认只有买方主动提交请求后才创建对外答复任务；MVP 工程师从工作台发布到买方原网页会话，同一浏览器可返回查看，买方也可自愿提供已有联系方式供销售人工回复。未留联系方式时不主动发送站外通知；具体恢复机制及隐私验收在开发时落实，不虚构回复时限。
- 询价与销售处理：RFQ 提交时必须确认可回复联系方式；需继续细化缺项的补充入口、卖家下一步操作和跨访问恢复规则。服务端保存状态不等于匿名买家可安全恢复会话。
- 采购阶段判断：MVP 第 1.2 节当前将中断且无后续回复标为“正在调研”。建议将可观察的会话中断与尚未知的采购阶段分开；这是待讨论的旧规则调整，当前未改写 MVP。

**首轮决定与剩余问题**：Q1 直接产品页入口、Q2 对话结合可编辑字段已确认并写入 MVP。Q3 已确认普通网页浏览与资料问答不强制留资；人工请求可只在原网页会话查看、无须邮箱/电话，也可选择自愿提供已有联系渠道，提交请求成功才建任务；RFQ 仍必须确认可回复方式。明确采购信号时如何提示、来自邮件/社媒的已有联系点如何核对仍待评估。MVP 当前只有网页买方入口及其他渠道手动来源标签，不因本轮讨论自动增加社媒/邮件消息接入。

**话术设计待验证**：围绕买方原问题说明已知事实、待核实点与可选下一步；使用专业、自然的表达，不隐瞒 AI 身份、不假称人工已介入。英文买方界面文案需由目标买家试读，具体句子不作为当前已验证的成交或信任效果。

**英文买方界面话术草案（占位场景，尚未定稿）**：买方问“这台泵能否用于 50°C 的介质”，且核准资料确实没有覆盖该条件时，可回复：

> Thanks — the liquid temperature matters here. The product information currently available doesn't confirm whether this model is suitable at 50°C. A product engineer can check it against your application. Would you like me to pass along your question and the details you've shared?

按钮可写 `Ask an engineer to review`、`Keep exploring`。买方选择前不写“已安排工程师”；选择后再说明“Where should we send the engineer's reply? We'll use this contact for this question.” 具体介质、温度、文档覆盖情况须来自该次会话与核准资料，不能把示例中的 50°C 当作任何型号的真实限制。

**后续评审顺序**：入口与交互 → 追问/确认/推荐 → 产品页信息层级 → 人工等待与恢复 → RFQ 与销售接手 → 企业首次发布 → 将确认的选择写成可观察的 UI 验收。保留本条评审起点，后续决定追加历史。

## 每次开发任务结束时的最小检查

1. 核对本次功能的需求与验收是否改变；若改变，写明是谁决定、何时决定、影响哪些模块。
2. 核对代码、测试/演示和部署的实际状态，再更新本页。没有证据时保持“开发中”或“未开始”。
3. 如改变了原决定，在相关文档保留变更原因；不要删除历史行。将相关文件纳入 Git 提交，以便追溯逐字差异。
