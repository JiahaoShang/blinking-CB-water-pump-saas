# MVP 开发执行计划｜当前由一名开发者负责

**状态**：开发组织方式已按 2026-10-02 的用户决定更新。2026-10-03 已将 GitHub `main` 的测试应用选择性导入当前开发工作树作为基线；原有测试通过不代表各模块通过现行验收，详见[代码核查与复用决策](现有代码核查与复用决策.md)。功能范围与验收以 [MVP 开发需求文档](MVP-开发需求文档.md)为准。

## 工作方式与开工条件

一名专职开发者负责应用骨架、M1–M7 的前后端、数据迁移、模块集成和技术验证。产品范围由项目负责人决定；产品技术事实、选型规则和对外页面仍须由企业授权人员核准。单人开发不等于开发者可代替买方、销售或工程师作业务判断。

此前双人计划建议 Next.js App Router、TypeScript、PostgreSQL，但 GitHub `main` 有 Python 标准库与 SQLite 的**测试应用**，现已导入开发工作树。它是可运行起点，不是经确认可直接投入正式开发的完整实现；技术选型仍可在接口、安全、部署和试点规模证据出现后复审。模块仍按产品知识、页面、会话、匹配、问答、RFQ、销售等业务边界组织，但不为单人分工建立额外服务或交接流程。

当前开发以本地 `feat/mvp-foundation` 工作树为基线，目标远端是现有 GitHub 仓库。本地主路径与 GitHub `main` 的 Git 历史及文档进度仍需安全合并，尚无自动同步；导入测试代码不等于已经把新改动推送到 GitHub。GitHub 仓库目前公开，已有文档、Demo 资料和测试代码；本地主路径还含概念线稿。统一仓库时须保留两边已有提交和内容，不用强制推送覆盖另一边。

继续开发时应核对现有启动说明、测试与数据迁移，并补齐缺少的锁定依赖、无密钥环境样例和从全新克隆可复现运行的步骤；不为了符合旧计划重建已经存在的应用。实际买方联系方式和密钥不提交 Git。已公开上传的 Lowara Demo 资料仅说明用户确认其公开 GitHub 上传授权；用于买方页面展示、下载或正式选型时，仍按该场景核对许可、型号、版次与企业核准状态。当前 Demo 文件夹只有一个具体型号，不能单独完成多型号推荐验收。

## 按业务链路逐段实现

| 检查点 | 主要工作 | 完成条件 |
| --- | --- | --- |
| 0 现状与工程底座 | 统一仓库；核对远端现有应用、登录、企业上下文、迁移、启动说明与自动检查并补齐缺口 | 全新克隆可启动；租户边界和共享 ID 有可运行样例；不把概念线稿或旧计划标为已实现 |
| 1 产品知识与页面 | M1 导入、来源定位、人工核准；M2 固定产品页、版本及获准文件的预览/下载 | 从界面核准并发布；未核准事实不能对外；两个不同适用条件的示例型号可展示 |
| 2 需求与推荐 | M3 对话、可编辑需求卡和确认；M4 基于核准事实与规则的候选比较；形成供企业官网聊天前端调用的标准 API 契约 | 已接入 API 的网页客户端在买方确认需求后才看到匹配候选；缺条件、硬冲突和多候选走各自正确路径 |
| 3 问答与人工 | M5 有出处问答、未解问题、买方请求、工程师同会话追问和答复 | 资料外问题不编造结论；人工回复在原会话可见，未提交请求不建任务 |
| 4 询价与销售 | M6 RFQ 与修订；M7 共享队列、任务处理和销售跟进 | 买方随时能发 RFQ、确认联系方式并编辑原记录；卖方看到初次与后续变化 |
| 5 联合收口 | 串联 M1–M7，验证网页聊天 API、版本、权限、故障回退、重复提交和恢复 | 通过卖家系统和一个调用标准 API 的网页聊天客户端完成主路径；跨企业访问被拒；重启及数据库与关键文件恢复演练通过。该客户端可以是企业自有窗口或演示参考组件，不要求开发自助安装与复杂配置 |

每个检查点先核对 GitHub 现有代码和验收证据，再补齐缺口，不因计划列出 M1–M7 就重做已有功能。进入下一检查点以通过当前必需验收为准，不预设完成日期。非阻断缺陷按[修复待办](开发状态与变更记录.md#修复待办)记录；未通过的必需验收不能标成已完成。检查点 1–2 所需的第二个型号和经核准的演示规则须先备齐，不能用同一型号的不同文件冒充两个候选。

## 模块间需要保持的契约

| 上游数据 | 下游使用 | 不可破坏的边界 |
| --- | --- | --- |
| 企业、成员与权限 | 所有模块 | 企业归属由服务端确认；公开页与私有会话分别授权 |
| 已核准产品事实、来源和版本 | 页面、匹配、问答 | 抽取草稿不作为确定性事实；撤回版本不进入新的推荐或回答 |
| 买方原话与需求修订 | 匹配、人工任务、RFQ | 区分提取值、买方确认值和未知项；修改后旧推荐失效 |
| 推荐依据及所见页面版本 | 问答、RFQ、销售记录 | 保留当时理由、缺项与版本，不因产品更新改写旧询价 |
| 人工任务、RFQ 与线索 | 买方原会话、销售工作台 | 买方提交请求后才建人工任务；RFQ 修订保留初次内容和历史 |

这些关系先在代码类型、数据库约束和针对性测试中落实；不为单人开发另建网络服务。每个检查点只迁移所需表，迁移要在空库和已有测试数据的数据库上验证。跨模块改动先核对上表及[数据模型草案](数据模型草案.md)，再调整实现。

## Git、验证与记录

每个可验证的小切片提交清楚的 Git 记录；高风险的鉴权、跨企业数据或迁移改动使用独立分支和 PR 检查差异。若没有第二位开发者，不将“另一人审核”设为虚假的完成门槛；能安排独立审查时优先审查上述高风险改动。工程骨架建好后，让自动检查覆盖类型、静态检查、构建和相应测试；自动检查不能代替页面操作和业务技术核准。

每个检查点在 PR 或[开发状态与变更记录](开发状态与变更记录.md)中保存提交号、使用的产品/规则版本、界面操作路径、实际结果、失败项与负责人。试点只部署已通过必要检查的提交。本地主路径的卖家线稿只是界面概念；远端已有应用切片也须逐项按 MVP 验收核对，不能仅凭 README 的描述认定全部完成。
