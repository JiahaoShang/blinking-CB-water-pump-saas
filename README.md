# 项目文档入口与开发阅读规则

本页回答三个问题：**现在做什么、各文档管什么、开发时该读哪些**。文档描述需求与设计；代码、数据库和部署结果才代表实际完成状态。

## 文档之间的关系

```text
当前开发阶段：MVP 开发需求文档
       │ 规定用户旅程、功能范围和验收
       ├── 技术架构草案：模块责任、数据流和技术约束
       │      └── 数据模型草案：MVP 对象关系、版本和来源
       └── 架构决策记录：技术措施的当前优先级、启用条件

下一阶段：V1 完整功能开发需求文档
       └── 继承 MVP 主链路，增加渠道、多角色协作等能力；不自动进入当前开发

未来候选：长期功能代办备忘录
       └── 记录价值、条件与归属；不等于已批准开发或确定排期
```

| 文档 | 主要回答 | 开发中的地位 |
| --- | --- | --- |
| [MVP 开发需求文档](MVP-开发需求文档.md) | MVP 要完成什么，用户如何使用，怎样验收 | 当前 MVP 功能范围的主要依据 |
| [完整客户旅程与界面验收](完整客户旅程与界面验收.md) | 已确认的买卖双方路径如何串起来，哪些页面决策仍待调研 | 跨模块阅读与联合验收索引；具体范围仍以 MVP/V1 文档为准 |
| [MVP 双人并行开发计划](MVP-双人并行开发计划.md) | 两位开发者怎样分工、交接和合并检查 | 协作计划；不代表应用已开始开发 |
| [V1 完整功能开发需求文档](V1-完整功能开发需求文档.md) | MVP 后的第一版增加什么 | 规划下一阶段；当前 MVP 不因写在此处就实现 |

## 开发任务如何选读

先读本页，再按任务选取相关章节；**不要求每次通读所有文档**。

| 本次任务 | 优先读 | 按需补读 |
| --- | --- | --- |
| 实现 MVP 某个模块或页面 | MVP 文档中对应模块、联动与验收 | 涉及的数据关系读数据模型；涉及跨模块、权限或 AI 回退读技术架构；涉及部署/冗余读架构决策 |
| 做数据库或接口设计 | MVP 对应流程 → 数据模型草案 → 技术架构草案的数据契约 | 涉及备份、地域或实例数量时读架构决策 |
| 开发 V1 功能 | V1 对应模块 → MVP 被继承的主链路 | 技术架构、数据模型及架构决策的相关章节 |
| 评估 SEO、营销序列、CRM、CAD 等后续能力 | 长期功能代办备忘录对应条目 | MVP/V1 的现有连接点；经明确纳入阶段后再写验收并开发 |
| 更改模型、数据库、部署或海外环境 | 架构决策记录 → 技术架构草案 | 受影响的 MVP/V1 验收和数据模型 |

## 出现差异时如何处理

1. **用户在当前任务中的明确要求优先**。如果它改变既有范围或决策，先指出影响，再同步更新相应文档；不要沿用旧规则悄悄实现。
2. **按问题归属判断**：MVP 功能与验收看 MVP 文档；V1 扩展看 V1 文档；冗余和部署优先级看架构决策记录；数据关系看数据模型与技术架构。不存在“某一个文档在所有问题上永远压过其他文档”的总顺序。
3. **草案和代办不能变成默认任务**。文档写着“建议、待确认、触发后做”的内容，要保留其状态。若两个文档对同一功能给出互相矛盾的要求，应列明冲突和影响；无法据已确认决定消解时，再请用户裁定。
4. **已实现状态单独核查**：文档里的“要做”不等于代码里“已做”。开发前检查现有代码、测试与部署，完成后记录变更和验证结果。

## 用户以后可以怎样下达开发任务

一般无需逐份指定文档。可以直接说：

> 请按 `README.md` 的规则开发 MVP 的 M1 产品资料导入与核准。先核对对应验收、数据关系和现有代码，说明发现的冲突，再实现并验证。V1 和长期代办暂不纳入本次范围。

如果任务有特殊边界，再补一句，例如“这次只做页面原型，不接真实数据库”或“本次要把 F-09 正式纳入开发，先更新需求与验收”。明确指定不读某文档也可以；若因此缺少必要约束，我会说明缺口及其对实现的影响。

## 一次开发任务具体怎么做

用户只需说清楚**本次目标**，例如“开发 MVP 的 M1 产品资料导入与核准”。可选地补充限制，例如“先做界面原型”“必须使用我提供的水泵资料”或“这次不接外部服务”。不用每次重写文档清单、提交规则和汇报格式。

执行者按以下顺序处理：

1. **确定边界**：读本页和对应需求章节，核对现有代码；把本次要完成的验收点列成简短清单。遇到会改变范围的实质疑问，先说明影响并请用户决定；不自行把 V1 或长期代办加入本次任务。
2. **实现并验证**：完成一个能运行的功能切片。按风险选择验证方式：页面交互用实际操作，数据规则用针对性测试，跨模块流程做端到端检查。代码注释只解释不明显的原因、边界或风险，不逐行复述代码。
3. **保存改动**：对已验证、范围完整的改动做清楚的 Git 提交。一次提交说明一件事，例如 `feat(product): add document review flow`；未完成的部分说明状态，不把它包装成已完成。
4. **同步状态**：只有需求、数据关系或架构决定实际改变时才修改相应设计文档；按验收证据更新[开发状态与变更记录](开发状态与变更记录.md)。不为了每次提交机械地改所有文档。
5. **交付给用户检查**：给出能打开的页面或文件、改动文件清单、验证方法及结果、尚未完成的部分，以及 Git 提交号（若已提交）。用户可以直接指出“哪一步、出现什么结果、期望什么结果”，执行者继续修复并复验。

**每次开发交付的简短格式**：

- 完成：本次实现的具体功能。
- 改动文件：主要文件及各自作用。
- 验证：执行了什么检查、结果如何；未执行的关键检查说明原因。
- 未完成：剩余范围、已知问题或待用户决定的事项；没有则写“无”。
- 记录：状态文档是否更新、Git 提交号；未提交则说明原因。

周报可在持续开发后按需生成，用于汇总进展、阻碍和下一步；**不要求每日写日报**，也不要求每个修复都写一篇报告。Git 提交保留细节，开发状态记录保留阶段结论。

### 先完成可用流程，再按影响修复

**用户已确认，2026-09-30**：先完成当前阶段约定的可用业务流程，按既定验收验证；通过必要检查后继续下一切片，不因外观打磨、推测性边界情况或非阻断缺陷反复扩大修复范围。该原则不自动删除既有验收要求。

| 问题类别 | 判断与处理 |
| --- | --- |
| 严重事故或阻断问题 | 数据丢失/跨企业泄漏、错误发布关键技术事实、核心流程无法完成，或未达到当前切片的必需验收。先处理受影响流程的阻碍；若有可靠回退可评估使用并记录。该问题不阻止推进不受影响的独立工作，但未解决的必需验收不能标为通过。 |
| 非阻断问题 | 当前约定主流程可用，影响有限、可恢复或有明确替代操作。将复现、影响、已知频率/未知频率、替代方式与暂缓原因写入[修复待办](开发状态与变更记录.md#修复待办)，说明后继续开发，不默认当场修复。 |

发生概率和影响程度共同决定处理顺序。“低概率”必须注明证据或“尚未测得”，不能仅凭猜测；低概率但可能导致数据丢失、越权或错误工程事实的问题仍可能是阻断项。未实际观察且无具体风险证据的假设，不默认扩展成修复任务。视觉和体验改进若没有违背约定验收，作为候选改进记录，不冒充软件缺陷。

修复待办在用户要求、再次出现/影响扩大、下次开发相关模块或准备相关发布时复审。保留原条目及原因，可决定修复、继续暂缓或不修复；不承诺每个条目最终必须修复。若修复范围持续扩大，先记录当前阻碍与影响，完成能验证的部分，继续不受阻的工作；必需验收存在缺口时明确报告，不能为了“完成”而隐去。

## 文档何时更新、旧版本如何保存

文档**不会自行同步**代码、部署或试点反馈。每项开发任务结束时，执行者应核对受影响的需求、数据和架构文档，再依据验收证据更新[开发状态与变更记录](开发状态与变更记录.md)。范围或决策发生变化时，正文反映当前有效要求，重要变化在变更记录中追加“旧决定、新决定、原因、影响”；不要悄悄删掉旧决定。Git 提交保留文件的逐字历史。尚未提交到 Git 的编辑不受 Git 历史保护，也不会自动备份到远端。

## 临时创意与每日回顾

当一次讨论产生影响项目的创意、需求变化、决定、问题或验证结果时，及时在[开发状态与变更记录](开发状态与变更记录.md)追加带日期、状态和来源的记录。临时创意先记为“待评估”，不自动改写已确认需求；用户确认进入开发后，再更新对应需求和验收。长期候选的详细用途继续放在[长期功能代办备忘录](长期功能代办备忘录.md)，事件记录引用它，避免重复维护两份要求。

### 用户怎样决定、执行者怎样更新

用户可直接在聊天中用功能名称或编号决定，单个或批量均可，例如“把 F-09 纳入 V1”“暂缓 CRM 同步”“现在开发 M1”。明确开发指令本身包含对该任务的授权，不要求再走一次确认流程。“很有价值”“可以考虑”“基本认同方向”仅代表评价或方向认可，不能推断为进入当前开发；“我同意”要能明确对应上一项具体方案，范围不清时只澄清不清楚的部分。

执行者在原功能条目更新**决策状态**和**目标阶段**，保留原编号、内容及决定来源；在开发状态与变更记录中追加“时间、旧状态、新状态、阶段、原因、用户决定或验证证据”。已纳入某阶段的功能同时更新该阶段需求与验收；缺少会影响实现的验收条件时，记录缺口并询问，不能虚构确定值。用户无需每天打开文档逐项确认，也无需把条目复制到新标题后删除旧条目。用户直接编辑文档也可作为输入，但执行者应先核对差异和冲突。

**需求是否采纳**与**实现到哪一步**分开管理：决策状态用“待评估 / 已确认 / 暂缓 / 不采纳”，目标阶段单列“MVP / V1 / 后续 / 未定”。实现状态仍用“未开始 / 开发中 / 已验证 / 已上线”。例如“F-09：已确认，V1，未开始”不等于该功能已经实现；“暂缓”或“不采纳”条目保留历史，不删除。已有 F-编号继续使用；新条目在原所属文档中分配稳定编号，事件记录引用它，不另建重复需求库。

### 哪些事情触发记录、何时写入

| 触发条件 | 例子 | 更新范围 |
| --- | --- | --- |
| 提出有具体用户结果的新功能，或要求新增、修改、删除功能/验收 | “买家能点击 CAD 部件提问”“RFQ 必须增加介质温度” | 建议先写候选；明确决定后更新对应需求与验收，并留变更记录 |
| 改变阶段、优先级或产品定位 | “把 WhatsApp 接入提前到 MVP” | 原条目状态、目标阶段及受影响的需求文档 |
| 形成或改变数据、权限、模型、部署等技术决定 | “产品更新不能改变旧 RFQ 的参数” | 相关数据/架构记录及受影响验收 |
| 出现可验证的进度变化或影响继续推进的问题 | 某切片通过验收、测试发现企业数据串读、模型服务不可用 | 实际状态与证据；问题解决后保留原发现和解决记录 |
| 用户明确说“记下来”，或证据推翻已记录事实 | “这个点以后再做，先记下”；原手册表明此前参数有误 | 对应记录及必要的有依据更正 |

重复表达、普通提问、措辞润色或“希望更好用”等尚无具体结果的想法，不默认新增需求。是否值得写入按上表判断；不能判断范围时先记录原意为待评估，不能将其改成正式需求。这里只更新受影响文档，不每次修改所有文件。

“及时”指**在当前这轮讨论处理完成、给出最终回复前**完成必要记录，并告诉用户记入哪里、状态是什么。长讨论在形成稳定结论时记录；开发进度在功能切片完成验证或确认阻碍时记录，不逐行记代码。若无法写入，明确说明未保存及原因。每日自动归档仍只读这些来源并汇总，不批准需求或更改状态。

每日回顾以本项目对话中可访问的内容、事件记录、Git 提交/差异和验收证据为依据，写入 Obsidian 的“跨境工业品AI销售平台/每日项目记录”。记录需求增改删、实际进度、重要决定、待评估创意、阻碍与下一步；每项结论注明来源。日报是回顾副本，不自动反向修改需求、验收或代码。没有证据的“已完成”不得写入日报。

自动汇总应记录覆盖区间；下一次从上次成功归档的截止时间继续，避免晚间截止之后或漏跑期间的信息丢失。同一天重复执行仅追加新信息或更正，保留用户手写内容和原归档记录；没有变化时可留一条简短“无新增”。定时任务只能总结已记录或可访问的内容，无法保证收集其他平台、未保存对话或其他项目中的事件。
